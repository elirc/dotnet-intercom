# Answer: M2 idempotent visitor send

1. **Side effects of one send** (`SendVisitorMessage.cs:47-115`): (a) maybe a new `Conversation` plus routing (team, SLA policy, assignee) plus `TeamMember.LastAssignedAtUtc` bump (`ConversationRouter.cs:59-67`); (b) a `Message` row; (c) `RecordVisitorMessage`: reopen and maybe start an `SlaTimer` (`Conversation.cs:103-127`); (d) `LastMessageAtUtc`/preview, `Visitor.LastSeenAtUtc`; (e) two SignalR events. Only (d) is naturally idempotent. A retry today creates a duplicate message. It **doesn't** create a second timer if one is running (`hasRunningTimer` guard), but if an agent replied in between, the retry starts a *new* NextResponse timer. For a retried first message it creates a **second conversation** and advances round-robin twice.
2. **Constraint.** `(VisitorId, ClientMessageId)` UNIQUE, with `ClientMessageId` nullable (Postgres treats NULLs as distinct, so legacy requests are unaffected). `(ConversationId, …)` fails the first-message case: on the retry `conversationId` is null, so the handler would create conversation #2 before it ever reached the message insert.
3. **Race.** Check-then-insert loses under concurrency: both requests see "not found". Insert-then-catch wins: the second `SaveChangesAsync` throws `DbUpdateException` whose `InnerException is PostgresException { SqlState: PostgresErrorCodes.UniqueViolation }` (optionally check `ConstraintName`). On catch: `ChangeTracker.Clear()` (the failed conversation/message/timer are still tracked), re-query the existing message by `(VisitorId, ClientMessageId)`, and return it with its conversation. Do the pre-check first anyway for the common sequential case. It's cheap and avoids an exception path. Because conversation creation and message insert are in **one** `SaveChangesAsync` (one transaction), the losing request also rolls back its duplicate conversation. That's the elegant part of choosing `VisitorId`.
4. **Re-sending events on replay.** Usually no: the original request already published. But the original may have committed and then died *before* publishing (notify-after-save, no outbox: `:107-112`). A replay is the only chance to deliver it, and the clients dedupe by message id anyway (`Widget.tsx:19-21`, `Inbox.tsx:42-44`). Re-publishing on replay is therefore the safer choice. It's cheap, and consumers are idempotent. Either answer is fine if it's reasoned.
5. **Retention.** The key lives on the `Message` row forever, costing a nullable uuid column plus a unique index. Alternatively, use a separate `IdempotencyKeys` table with a TTL cleanup job (G6-style Hangfire job). On-row is simpler and has no cleanup.

**Backward compatibility.** `SendRequest` gains an optional `ClientMessageId` (`WidgetController.cs:37`), so old bundles send nothing and behave as before. Don't make it required for 7+ days. Log the rate of keyless requests and remove support when it hits ~0.

**Widget.** Generate the id when the user presses Enter, keep `body` until success, and retry with backoff (3 attempts) using the same id. Show a "failed, tap to retry" state.

**Schema change without migrations:** see M1 §6. It needs a `CREATE UNIQUE INDEX CONCURRENTLY … WHERE "ClientMessageId" IS NOT NULL`.

Rubric: Basic = sequential dedupe with a pre-check. Solid = + DB unique constraint, concurrent test, legacy path. Strong = + first-message/second-conversation case, ChangeTracker cleanup, reasoned replay-publish decision.
