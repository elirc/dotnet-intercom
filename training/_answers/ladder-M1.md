# Answer: M1 inbox query at scale

## Expected findings
1. **Generated SQL.** One query joins `Conversations` to `Visitors`, `Teams`, `AgentUsers` (reference navigations, cheap) and `LEFT JOIN SlaTimers` (a collection). EF Core 8 single-query mode returns one row **per timer** for each conversation in the page. Paging is applied to conversations in a subquery first (EF wraps `Skip/Take` before the collection join), so rows = Σ timers of 25 conversations. The real killer is **what the subquery must sort**: `ORDER BY LastMessageAtUtc DESC` over all `Open` rows. The `(State, LastMessageAtUtc)` index (`AppDbContext.cs:72`) serves it. That's why `lastMessage` is "only" 900 ms, the cost being mostly `COUNT(*)` plus the timer join.
2. **slaBreach sort.** `ORDER BY COALESCE((SELECT MIN(BreachAtUtc) FROM SlaTimers WHERE ConversationId = c.Id AND Status = 0), 'infinity')` is computed per candidate row. It's a correlated subquery for **every open conversation**, followed by a full sort. The `(Status, BreachAtUtc)` index is keyed by status first, not by conversation, so it can't give a per-conversation min. Fixes: (a) an index on `SlaTimers(ConversationId) WHERE Status = 0` (partial) to make the subquery cheap; or (b) better, denormalize `Conversation.NextBreachAtUtc` (nullable), maintained in `RecordVisitorMessage`/`RecordAgentReply`/`Close`/`MarkBreached`, with an index on `(State, NextBreachAtUtc)`. The invariant is "NextBreachAtUtc = min BreachAtUtc of running timers". It's owned by the `Conversation` aggregate, so it's enforceable in one place, but `CheckSlaBreachesHandler` must also clear it.
3. **Projection.** Project `ActiveTimer = c.SlaTimers.Where(Running).OrderBy(BreachAtUtc).Select(...).FirstOrDefault()` and `HasBreached = c.SlaTimers.Any(Breached)` directly in a `Select` to a DTO. You get two scalar subqueries instead of loading the whole timer history (a conversation open for a year could have hundreds of timers).
4. **COUNT.** `CountAsync` on an `Open` filter reads the whole matching index range on every page load, ×25 agents × every realtime invalidation. Options: return `hasMore` (fetch `pageSize+1`), cache counts for 30 s, or show "50+". Keeping `TotalCount` in the response is required, so fill it with an approximate or capped number (`Math.Min(count, 1000)` via `LIMIT 1001` in a subquery) and document it.
5. **Search.** `lower(x) LIKE '%term%'` can't use a B-tree. Use `pg_trgm` GIN indexes on `lower(Subject)`, `lower(Visitors.Name)`, `lower(Visitors.Email)` (or `ILIKE` with trigram ops). Writes cost more: every message updates `Conversation` (preview/last-message), but the index is on `Subject`, which doesn't change, so the cost is small. Visitor email/name trigram indexes are cheap.
6. **Shipping indexes with no migrations.** `EnsureCreated` won't add indexes to an existing DB. Options: introduce migrations first (baseline migration marked applied via an `__EFMigrationsHistory` insert, see S1), then add a migration with `migrationBuilder.Sql("CREATE INDEX CONCURRENTLY …", suppressTransaction: true)`. Or run the DDL out-of-band with a runbook. `CONCURRENTLY` can't run inside a transaction and can leave an `INVALID` index on failure, so check `pg_index.indisvalid`.

## Also expected: the load multiplier
Every `messageCreated` makes **every agent** refetch the list (`Inbox.tsx:41,47`). With 25 agents and 5 messages/s, that's up to 125 list queries/s from invalidations alone. Fixes: patch the cached row from the event payload (`setQueryData`) instead of invalidating, or debounce invalidations (e.g. 1 s). The strongest answers fix both the query and the multiplier.

## Regression guard
An integration test with EF logging/`DbCommandInterceptor` that counts commands and captures SQL for the list call. Assert ≤ 3 commands, and assert the SQL doesn't contain a `LEFT JOIN "Messages"`. That also catches incident 005.

Rubric: Basic = adds an index. Solid = + projection instead of include, partial index or denormalized column, EXPLAIN evidence. Strong = + COUNT strategy, trigram search, CONCURRENTLY rollout, and the realtime invalidation multiplier.
