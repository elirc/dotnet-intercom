# Answers: 20 technical questions

1. Over REST you get the MediatR pipeline (validation, logging), rate limiting (`[EnableRateLimiting("widget")]`), status codes, and an idempotency key if you add one. It's testable with `HttpClient` and retryable by any client. Over the hub, a dropped socket makes the send's outcome unknown, the policies are different, and all of that is gone.
2. It exposes internal fields (SLA deadlines, team, assignee ids, `HasBreachedSla`, the preview, which could leak a note: incident 001). Return a `WidgetConversationDto` (id, state, assigneeName) built by an allow-list, the same shape the hub already sends (`RealtimeNotifier.cs:32-37`).
3. It gives "everything strictly newer than T". It breaks on equal timestamps (same batch or same µs) with `>` (`WidgetQueries.cs:36`, `GetConversation.cs:53`), and on client clock or format issues if the client builds T itself. Fix: a composite `(CreatedAtUtc, Id)` cursor or a monotonic sequence.
4. `/widget/*` has old clients in the wild you can't force-upgrade: add-only changes, optional new fields, and nothing removed for at least the cache TTL (measure it). `/conversations/*` ships with the inbox, so breaking changes are fine with a coordinated deploy (open tabs need a reload).
5. It protects concurrent updates of the `Conversation` row (assign/close/snooze/last-message). It doesn't cover `SlaTimer`, `TeamMember` (round-robin) or `Message`. When it fires, the result is an unmapped `DbUpdateConcurrencyException` → 500, logged at Error (ladder J1).
6. The subquery runs per candidate row and the result must be sorted in full, and the `(Status, BreachAtUtc)` index isn't per conversation. Fixes: a partial index `SlaTimers(ConversationId) WHERE Status = 0` (cheap, still per-row work), or a denormalized `Conversation.NextBreachAtUtc` + index (fast, but it's an invariant to maintain in every timer transition).
7. Both `FirstOrDefaultAsync` miss, both add a `Visitor`, and one `SaveChangesAsync` hits the unique index on `AnonymousId` → `DbUpdateException` → 500 in that tab (`StartConversation.cs:51-57`). Fix: catch 23505, clear the tracker, re-query. Or `INSERT … ON CONFLICT DO NOTHING` then select.
8. `EnsureCreated` never alters an existing DB, so first create a baseline migration and mark it applied, then add a migration with `CREATE INDEX CONCURRENTLY` (`suppressTransaction: true`), run it from a pre-deploy step, and check `indisvalid` afterwards.
9. Each worker's `DbContext` loads the timer as `Running`, and `MarkBreached` passes in both (the guard is in-memory). Both `UPDATE`s succeed because there's no concurrency token on `SlaTimer`, so there are two `slaBreached` pushes. There's no exception. The architecture review's claim is wrong.
10. Both read the same minimum and assign the same agent, then both write `LastAssignedAtUtc` (a lost update). At low volume it's harmless. At peak it skews the load. Fair options: `SELECT … FOR UPDATE SKIP LOCKED` on the team member row inside the transaction, or an atomic `UPDATE … RETURNING` that picks and stamps in one statement.
11. Recurring jobs are persisted by id. A per-host id creates a separate schedule per host, never cleaned up, which accumulates across deploys (host names change): N concurrent sweeps per minute (incident 003).
12. The connection id changes, so every group membership (`vconv:{id}`, `conv:{id}`), `Context.Items` and per-connection presence entries are gone. The widget never rejoins `vconv:{id}`, so it receives no pushes until reload (ladder M3).
13. Each mount adds another set of handlers to the singleton connection, and the old ones are never removed. After three round trips, each event triggers 4× invalidations and 4× `setTyping`/`setViewers`, and closures from unmounted components call setters on stale state. Fix: `conn.off(name, handler)` in cleanup, or register handlers once, outside components.
14. With 25 agents × every message plus every `conversationUpdated`, you get list refetches at events × agents per second, each a heavy query (M1, incident 005). Instead: patch the cache from the event payload, debounce invalidations, or refetch only when the event affects the current filter.
15. `externalId` comes from the browser, so anyone can claim `user-42` and receive their token and history. The fix: the customer's **backend** computes `HMAC-SHA256(key = workspace identity secret, message = externalId)` and renders it into the snippet as `userHash`. The API recomputes and compares in constant time (`CryptographicOperations.FixedTimeEquals`), and without a valid hash it ignores `externalId`.
16. The base config applies in every environment. A fresh production DB gets `admin@netintercom.local / Passw0rd!` (`DbSeeder.cs:11, 39`), a credential documented in the README and on the login page. That's a known-default-credential vulnerability (OWASP A07).
17. The widget authenticates with a bearer header, not cookies, so a malicious origin can't ride an ambient credential. It becomes exploitable the day any widget endpoint accepts a cookie (e.g. someone moves the visitor token into a cookie "for security"). Then any site could make credentialed calls. Drop `AllowCredentials()` now.
18. Routing depends on the wall-clock UTC time, because Billing has office hours from 08:00 to 18:00, so the exact team varies with when CI runs. Inject a fake `IClock` in `ApiFactory` (replace the singleton) and assert `teamName == "Billing"` in-hours and `"Support"` out-of-hours in two tests.
19. `Program.cs:128-130`: there's no exporter (`AddOtlpExporter`), so traces go nowhere. Instrumentation is ASP.NET Core only (no EF/Npgsql/Hangfire/SignalR). There are no metrics at all. Incident 002 needs presence transitions/min, the unassigned ratio and hub connects/disconnects, and none of those exist.
20. (1) Did routing rules, teams or office hours change? (DB + deploys.) (2) Is it bursty or steady? Correlate with hub disconnect/reconnect metrics and login waves. (3) The router logs "No online agents in team …": which teams? (4) Presence as the router sees it vs the UI (`GET /agents` presence vs the dots), which rules the tracker in or out. (5) The recent deploy diff touching presence/routing. Then reproduce: disconnect one agent and query `GetOnlineAgentIds` within 60 s.
